# Prompt: Build the Market Risk Prediction System UI

Read `prompt.md` completely and inspect the existing project, backend APIs, trained models, prediction logic, and frontend structure.

Your task is to build the **frontend UI only** for the existing Python-based Market Risk Evaluation and Prediction System. Do not rewrite the backend or retrain models as part of this task.

The most important requirement is a **Historical Prediction Comparison page** that allows users to select past dates and compare actual historical market values with predictions generated by the model for those same dates.

## 1. Primary Feature: Historical Prediction Comparison

Build a dedicated page called **Historical Backtesting & Prediction Comparison**. Make this page easy to access from the main navigation.

The purpose is to evaluate model performance using historical data rather than waiting for future market dates.

### C. Choose What to Compare

### D. Historical Prediction Methodology

The historical comparison must be methodologically valid.

First inspect whether the backend already supports historical predictions, stored prediction records, or walk-forward backtesting.

Use the existing implementation where possible. If the backend does not support historical evaluation, document the required backend functionality and API contract instead of pretending that the UI can produce valid results independently.

For valid historical testing:

1. Use only information that would have been available at the prediction timestamp.
2. Generate each prediction using the selected model and the features available at that time.
3. Ensure training data does not include future information relative to the prediction timestamp.
4. Apply the model's intended forecast horizon and target definition consistently.
5. Compare each prediction against the actual outcome for the corresponding target date.
6. Exclude or mark dates for which the actual outcome is not yet available.
7. Account for market holidays, weekends, missing observations, and trading calendars.
8. Clearly distinguish historical predictions generated without future-data leakage from retrospective model fits that may have seen the evaluation period.

Prefer **walk-forward or rolling-origin evaluation**: for each evaluation date, use only training data that would have been available at that point. If the backend only provides retrospective predictions, label them clearly and do not present them as leakage-free backtests.

- Actual vs. predicted performance by forecast horizon.
- Baseline model performance, if available.

Calculate or retrieve these metrics using genuine actual and predicted values. Use backend metrics when available; otherwise, calculate them in the frontend only when the necessary data and metric definitions are available and the computation is appropriate.

Do not invent performance numbers. Show unavailable metrics as “N/A” and explain why.
